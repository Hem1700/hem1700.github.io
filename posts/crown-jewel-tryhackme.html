The Crown Jewel: reconstructing a full attack chain from PCAP and Splunk

Sep 19, 2026 · 9 min read

Reverse Shell Outbound Connection Detected — severity: High.

Most of what ends up on this page is source-level: a missing check, an unchecked index, a sanitizer catching what review didn't. This one's the other half of the job. Given only network telemetry — a raw pcap and a Splunk index, nothing else — reconstruct what an attacker actually did, in order, and prove it with evidence instead of assumptions. No source, no stack trace, just packets and logs, and the discipline of not skipping a step because it seems obvious.

This is a writeup of TryHackMe's The Crown Jewel, a DFIR/network-forensics room built around exactly that: one High-severity alert, and two artifacts to work from — challenge.pcap and Splunk's index=network_logs. The job is to go from “something phoned home” to a complete, evidenced kill chain, and identify exactly what was taken.

1. Method: work both sources in parallel

Wireshark is faster for “what does this one packet actually say.” Splunk is faster for “how many times did this happen, and when.” Bouncing between the two turned out to be the efficient path: use Splunk to find the anomaly, then Wireshark to read the raw bytes behind it.

Splunk's network_logs index holds five multiplexed log types under one sourcetype, distinguished by a log_type field: arp, dns, http, ids, and netflow. All tagged host=lab at the Splunk metadata level, with the real per-service hostname (jira, etc.) nested inside the JSON body — worth knowing up front, since a naive host=jira filter silently returns nothing.

index="network_logs" | stats count by log_type, host
log_type   host   count
arp        lab    90
dns        lab    1733
http        lab    1802
ids        lab    1      <-- one event. that's the alert itself.
netflow    lab    1435

That single ids event became the whole investigation's anchor point.

2. Reconnaissance: subnet sweep

Wireshark's TCP conversation list showed a single host issuing hundreds of one-packet, 54-byte connections across 10.10.10.0/24, exclusively on ports 22/80/443 — SYN, RST, nothing else. No payload, no banner grab, just presence-checking. Textbook T1595 — Active Scanning: map what's alive and what's listening before touching anything.

3. ARP spoofing: inserting a man in the middle

Pulling the ids event directly gave the anchor for everything downstream:

{
  "msg": "Reverse Shell Outbound Connection Detected",
  "src_ip": "10.10.10.100",
  "dest_ip": "1.1.1.1",
  "dest_port": 8080,
  "proto": "TCP",
  "severity": "High",
  "sid": "SID:2100498"
}

src_ip was tagged host: jira — the Jira server was the one that got popped and called home. But before that, the ARP log told a quieter, earlier story:

index="network_logs" log_type="arp" "event.sender_mac"="00:0c:29:11:22:33"
| stats count by "event.sender_ip"
event.sender_ip   count
10.10.10.1         45
10.10.10.150        45

One MAC, 00:0c:29:11:22:33 — a VMware OUI, so an attacker VM rather than a physical router — sent 90 gratuitous ARP replies split evenly across two identities. It told 10.10.10.150 “I'm the gateway,” and told the real gateway “I'm 10.10.10.150.” Classic bidirectional poisoning (T1557.002): every packet between that host and the network now transits the attacker first, in both directions, without either side observing a routing anomaly.

4. Credential theft: MITM only pays off without TLS

Splunk's parsed HTTP fields didn't carry POST bodies, so this part went back to Wireshark — find the one “HTML Form URL Encoded” packet the protocol hierarchy had already flagged as the sole occurrence of that content type in the whole capture.

Edit → Find Packet → Packet bytes → "password"

That landed on frame 4891 — 10.10.10.150 → 10.10.10.1, POST /login.php. Following the TCP stream:

POST /login.php HTTP/1.1
Host: internal.login.local
Content-Type: application/x-www-form-urlencoded

username=dev_user&password=SecretPassword!

Plaintext, because the internal login endpoint never enforced HTTPS. ARP spoofing alone doesn't hand you credentials — it hands you a front-row seat. It's the missing TLS that turns that seat into a payday. That combination — spoofed routing and an unencrypted internal login form — is the actual vulnerability here, not either piece alone.

5. Exploitation: a signature that gives itself away

index="network_logs" log_type="http" extracted_host="jira"
| stats count by "event.agent"
event.agent                                          count
CVE-202X-EXPLOIT                                       1
curl/7.68.0                                            393

Mozilla/5.0 (Windows NT 10.0; ...) Chrome/100...        363
Mozilla/5.0 (Macintosh; ...) Safari/605.1.15            350

One request out of 1,802 carried a User-Agent that names its own CVE. It hit /vulnerable_endpoint?cmd=RCE on the Jira host — T1190, Exploit Public-Facing Application. This is the foothold that the IDS alert's src_ip (10.10.10.100) traces back to.

6. Command and control

The IDS event already gave this one directly: 10.10.10.100 → 1.1.1.1:8080, TCP. Following that stream in Wireshark showed only a handful of small packets — the shell was either short-lived or caught fast — but the callback itself is T1071, and it's what tripped the original detection that started this whole investigation.

7. Exfiltration: DNS as a covert channel

index="network_logs" log_type="dns" | stats count by "event.query"

Hundreds of rows, each a unique, high-entropy subdomain, count=1 every time, all under one parent:

0c1ms56uqp9hqy2ga89jzyjv9otv5fbn.exfil-domain.xyz
0f9o4zqvsf4yr7b9z32b162s6sageuv2.exfil-domain.xyz
0ghn16cpuv3nl8okquiytww39eofi4xg.exfil-domain.xyz
...

exfil-domain.xyz — attacker-owned, and the subdomain labels aren't lookups, they're payload: the “Crown Jewel” data (GitLab/Jira proprietary source) chunked and smuggled out one DNS query at a time. T1048.003. DNS is close to universally permitted outbound even on networks that lock down everything else, which is precisely why this works.

Takeaway

None of these six steps is exotic on its own: a scan, a spoofed ARP entry, a plaintext form, a known CVE, a shell, a DNS query. What makes it a real incident is that each weak link fed the next one cleanly, and no single control caught the chain in the middle. That's the same lesson as reviewing code for the missing bounds check: the interesting bug is rarely the one nobody thought about — it's the one invariant that held everywhere except here.

Tools: Wireshark, Splunk (index=network_logs). Full IOC list above.
