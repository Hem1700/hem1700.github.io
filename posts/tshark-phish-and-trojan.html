TShark Challenge I and II: Directory

Sep 21, 2026 · 7 min read

A user came across a poor file index, and their curiosity led to problems.

Two TryHackMe rooms, back to back — TShark Challenge I: Teamwork and TShark Challenge II: Directory — both built around the same discipline: read a pcap with the command line, not a GUI, and pivot every suspicious indicator through VirusTotal until it's an evidenced verdict instead of a hunch. No Wireshark clicking, just tshark -Y filters and field extraction, which is closer to how this actually goes when you're working a case over SSH with no X11 forwarding.

Two small cases, two different endings: one victim who typed a password into a spoofed login form, and one who double-clicked an executable sitting in a wide-open Apache directory listing.

Case 1: the PayPal page that wasn't

Start every pcap the same way — what did it try to resolve:

tshark -r teamwork.pcap -Y "dns.flags.response==0" -T fields -e dns.qry.name | sort -u
toolbarqueries.google.com
wittyserver.hsd1.md.comcast.net
www.paypal.com4uswebappsresetaccountrecovery.timeseaways.com

One entry doesn't belong. www.paypal.com4uswebappsresetaccountrecovery.timeseaways.com puts paypal.com right at the front where a skimming eye lands, but the actual registrable domain — the part a browser's address bar and a WHOIS lookup both care about — is timeseaways.com. Everything in front of it is attacker-chosen subdomain, free of charge, no registration needed.

Pulling the request paths confirms it's a full kit, not just a landing page:

tshark -r teamwork.pcap -Y 'http.host contains "timeseaways"' -T fields -e http.host -e http.request.uri
/
/inc/login.php
/inc/visit.php
/inc/suspicious.php
/img/shield.png
/font/PayPalSansSmall-Medium.woff2
/js/jquery.creditCardValidator.min.js?_=1492480834539
/img/logo_ccVisa.gif
...

PayPal's actual web font, a credit-card validator script, brand icons — this is a cloned account-recovery flow, not a one-page lure.

VirusTotal: confirm, then split root from subdomain

Searching the full URL on VirusTotal gives a verdict (2/90 malicious) and a first-submission date of 2017-04-17 22:52:53 UTC — this kit has been sitting around, previously caught, for years. But the interesting split shows up when you search the bare registrable domain instead of the phishing subdomain: timeseaways.com comes back clean, 0/89, registered on GoDaddy roughly 22 years ago, category "travel," with legitimate-looking MX records pointing at Google. That's not a domain someone bought to phish with — that's a real travel site whose DNS or hosting got abused to host a subdomain its owner probably never knew existed. The distinction matters operationally: takedown and remediation for "compromised legitimate domain" looks completely different from "attacker-registered domain."

The phishing subdomain's own passive DNS record (VirusTotal's Relations tab) resolves it to 184.154.127.226, dated the same day as the first submission — one consistent timeline, not a coincidence.

Reading the harvest straight off the wire

Splunk or VirusTotal won't have this part — it's only in the pcap. The phishing kit's own login endpoint:

tshark -r teamwork.pcap -Y 'http.request.method=="POST" and http.host contains "timeseaways"' -T fields -e http.host -e http.request.uri -e urlencoded-form.value
/inc/login.php   johnny5alive@gmail.com,johnny5alive,Mozilla FireFox v43,Linux,Desktop Platform,
                 Mon Apr 17 2017 22:00:35 GMT-0400 (EDT),Computer: 1920x1080,en-US

Plaintext email, plaintext password, browser fingerprint, timestamp — all POSTed in the clear, and all matching the VirusTotal submission timestamp to the minute. Whoever ran this kit had the victim's real credentials the moment the form submitted.

Case 2: the directory listing nobody should have left on

Same opening move, different capture:

tshark -r directory-curiosity.pcap -Y "dns.flags.response==0" -T fields -e dns.qry.name | sort -u
api.bing.com
tecvlist.microsoft.com
jx2-bavuong.com          ← odd one out
ocsp.digicert.com
r20swj13mr.microsoft.com
www.bing.com

Everything else here is Windows/Bing/DigiCert telemetry — background noise any machine generates. jx2-bavuong.com has no brand, no recognizable pattern, and it's the one VirusTotal flags: 4/89, tagged "known infection source" and malicious by alphaMountain.ai.

Fourteen HTTP requests went to it over the capture:

tshark -r directory-curiosity.pcap -Y 'http.request and http.host contains "jx2-bavuong"' -T fields -e frame.number | wc -l

and every response carried the same fingerprint — worth grabbing on its own, since a stale, versioned web stack is itself a signal:

Apache/2.2.11 (Win32) DAV/2 mod_ssl/2.2.11 OpenSSL/0.9.8i PHP/5.2.9

One useful lesson from this step: VirusTotal's domain report shows whatever it currently resolves to, which won't necessarily match what the traffic in your capture actually hit. Pulling the IP straight from the HTTP conversation in the pcap instead:

tshark -r directory-curiosity.pcap -Y 'http.host contains "jx2-bavuong"' -T fields -e ip.dst -e ip.src | sort -u
141.164.41.174    192.168.100.116

192.168.100.116 is the victim (RFC1918, obviously local); 141.164.41.174 is the real server this capture actually talked to — not whatever VirusTotal's passive DNS shows today.

Following the stream: an actual "Index of /"

tshark -r directory-curiosity.pcap -Y "tcp.stream==0" -q -z follow,tcp,ascii,0

buried in the ASCII is a plain Apache autoindex page:

<h1>Index of /</h1>
123.php       12-Jul-2020 08:43    1
vlauto.exe    06-May-2020 23:32   40K
vlauto.php    10-Jul-2020 23:25   93

Three files, no index.html to hide the listing, and a 40K Windows executable sitting right next to two small PHP scripts — a dropper page and probably a companion controller script. This is the entire premise of the alert: a user browsed to a bare directory index and clicked the one file that looked interesting.

Pulling and hashing the payload

tshark -r directory-curiosity.pcap --export-objects http,./http_objects
sha256sum ./http_objects/vlauto.exe
b4851333efaf399889456f78eac0fd532e9d8791b23a86a19402c1164aed20de

(Four identical copies got exported — the same 41315-byte file, fetched across several connections in the capture, all hashing the same.)

That hash on VirusTotal isn't ambiguous: 40+ of 89 engines flag it, mostly clustering around one family — Backdoor:Win32/Blubot, MSIL/Agent.PJE, Gen:Variant.Jalapeno — and the dynamic engine agrees: Lastline Sandbox classifies it as MALWARE TROJAN. Static signatures and a sandboxed detonation landing on the same answer is about as close to certainty as this kind of triage gets.

The rest of the capture backs that up nicely. After the download, the host starts polling a set of bot-panel-shaped endpoints on the same server:

GET /newbot/proxy
GET /newbot/blog
GET /newbot/target
GET /newbot/target.method
GET /newbot/target.ip
GET /newbot/target.port
GET /newbot/botlogger.php

All 404. Read together with the "Blubot" family name in the AV signatures, this looks like exactly what it sounds like — a bot checking in with its command-and-control panel for a target to attack, on a panel that's since been taken down or was never fully configured. The malware is still trying to phone home; there's just nobody answering anymore.

Takeaway

Neither case needed anything clever — both fell out of the same two-line habit: dump every DNS query the host made, and eyeball which one doesn't belong. A domain with a brand name jammed into its subdomain, or a domain with no brand at all, both stand out from real infrastructure the instant you sort the list. Everything after that is confirmation: VirusTotal to turn suspicion into a verdict, --export-objects and a hash to turn a suspicious download into a named, cross-checked malware family. The tooling barely matters. The habit of listing every domain a host talked to, before deciding any of them are boring, is the actual control here — the same discipline as diffing a function against its siblings before deciding it's fine.
